# 表情贴图技术调研与双方案对比

日期：2026-09-19；目标：Cocos Creator 3.8.8、单人微信小游戏。

## 结论

目前需求主要改变眼睛和嘴巴的图案，不要求明显改变脸部轮廓，适合先采用贴图表情。保留两条美术路线：平面眼睛＋贴图嘴巴，或立体眼球＋贴图嘴巴。推荐共用一套表情状态与图集配置，眼睛的表现层可替换；不必先投入完整面部骨骼。

本轮已完成独立技术对比页：`http://127.0.0.1:4179/expressions.html`。同一个实际头模左右并排，支持视线随操作方向移动、同步转动、两种头型、平静/开心/惊讶/生气/难过哭泣，以及自动和手动眨眼。原理得到独立 WebGL 预览验证，尚未接入 Cocos 的角色材质或微信真机；原理可迁移不等于已经验证引擎与平台兼容性。

## 两种方案的区别

| 项目 | 平面五官 | 立体眼球＋贴图嘴巴 |
| --- | --- | --- |
| 眼睛 | 贴在脸部曲面上，图案替换很自由 | 球面有厚度，可追加转眼和视线跟随 |
| 眨眼 | 图集闭眼帧，左右眼可独立 | 需要眼皮/遮罩，不能只隐藏眼球露出眼洞 |
| 开心眯眼、夸张符号眼 | 容易直接画成弧线、星星等 | 通常需要眼皮形变，符号眼可临时切平面表现 |
| 嘴巴 | 图集切换笑、惊讶、抿嘴等 | 相同的贴图口形方案 |
| 侧面 | 没有眼球凸起，口形随表面透视缩窄 | 眼球凸起更明显，嘴巴仍不会真正张开 |
| 美术准备 | 稳定面部 UV、图集 | 额外眼球与眼皮，局部位置和闭合规则 |
| 性能方向 | 可在原头部不透明材质内完成 | 眼球合并后通常多一个网格绘制，具体依材质/批处理决定 |

对比页已从纵向缩放眼球改为按开合量裁切眼部可见区域，眼球本体用于转动视线。这仍是眼睑遮罩近似，不是真实眼皮几何；对于带眼洞或明显眼皮厚度的正式角色，需要制作对应眼皮。两侧复用同一套占位图案，不能将本页五官质量当作最终角色美术。

## 贴图应该贴在哪里

优先把五官采样合成到头部自身材质的底色中，而不是在镜头前叠两个 UI Sprite：

1. 头部拥有面部 UV 和五官区域遮罩，五官位置随头部表面与姿态移动。
2. 眼睛、眉毛、嘴巴从同一张图集的不同区域采样，透明像素仅用来混合肤色。
3. 最终头部仍输出不透明颜色并正常写深度，头发、鼻子等正常参与遮挡。
4. 换表情只改图集矩形/帧号等材质参数，不新建头部网格、不重绘整张脸部贴图。

普通 Unlit 材质已经支持主贴图与 UV 缩放偏移，足以演示整张脸换帧；眼睛、眉毛、嘴巴需要独立状态时，应做专用 Effect，而不是用一个 `tilingOffset` 同时移动全部五官。[Cocos 3.8 Unlit 文档](https://docs.cocos.com/creator/3.8/manual/en/shader/effect-builtin-unlit.html)

独立的贴脸曲面片也是备选，适合不能改原材质的角色，但需要处理曲面适配、Z-fighting、侧面悬空、遮挡和透明排序。当前项目可以控制头部材质，所以不优先增加这层几何。

## 当前对比稿做了什么

- 沿用导出的真实头模及平滑颜色；`createCharacter` 增加可选关闭占位五官的参数，默认路径不变。
- `preview/expression-art.js` 在页面初始化时一次性生成 1024×512 RGBA 占位图集，随后一次上传到每个预览的 WebGL 上下文。切表情不再生成图像。
- 临时以头部局部 X/Y 计算面部坐标，并限制正脸 Z 区域；避免同一图案投到后脑。用头部坐标而非屏幕坐标，所以转头时五官贴住头模。
- 眼白与瞳孔占位图层分离：平面方案只移动瞳孔采样，在眼白区域内裁切；立体方案围绕眼球中心转动现有几何。开合遮罩独立覆盖眼睛，开心或哭泣时眨眼不会改变嘴巴。
- 两个头型的模型缓冲只在切换头型时更新，切表情只改参数。可见页面以 30 Hz 更新轻量行为计时器，只有视线、眉毛或开合量变化时重绘；隐藏页面暂停计时和绘制，返回不追赶播放眨眼。
- 当前没有加载头发；转头贴合与背面不重复投影已直接验证，头发遮挡仍需正式集成后在引擎内验证。

局部投影只适合这两个约定朝向的测试头，不是通用人物自动贴图算法。对于大鼻子、夸张侧脸、不同五官比例或左右不对称的模型，应使用正式 UV/独立面部区域标记与逐角色锚点配置，不能继续套固定坐标。

## 正式资产需要提供什么

| 资产/约定 | 要求 |
| --- | --- |
| 头部 | 正面朝向、中心、单位一致；保持完整皮肤表面 |
| 面部 UV | 眼嘴区域有足够像素，接缝避开五官，左右眼不能不可区分地镜像共用 |
| 皮肤底图 | 不烘死瞳孔、嘴型、眼皮表情，避免替换后残留两套五官 |
| 表情图集 | 各帧固定画布与锚点；透明边缘扩色、留 padding；嘴巴和左右眼可独立组合 |
| 立体方案 | 眼球/瞳孔/眼皮分清职责，至少提供左右闭眼形变或可用的眼皮遮罩 |
| 适配数据 | 左右眼、眉毛、嘴巴的区域与局部位置；不同脸型逐个验收 |
| 头皮 | 独立保持现有根绑定和生长区域，眼嘴切图不得触发头发重建 |

当前 JSON 主要导出位置、法线、索引和头皮绑定，没有正式面部 UV、眼皮骨骼或表情形态数据。后续需要扩展导出格式/改走合适的模型导入管线，并更新头部材质；不是换几张 PNG 就完成任意模型接入。

如果以后需要张嘴有深度、露出侧面牙齿、鼓腮或大幅改变下颌，再增加少量 BlendShape/Morph 或颌骨。Cocos 3.8 的 MeshRenderer 与网格数据支持 morph，但仍需为具体角色制作并验证目标形态。[Cocos 3.8 三维渲染 API](https://docs.cocos.com/creator/3.8/api/en/3d-rendering-readme)

## 建议的运行时接口

建议分开 `FaceExpressionController`（情绪、眨眼、说话优先级）、`FaceAtlasConfig`（帧和区域）与 `FaceAppearance`（材质参数、可选眼球/眼皮）。App 只发送语义事件。

状态例：`emotion=happy`、`leftEye=closed`、`rightEye=smile`、`mouth=smileOpen`，而不是为每个组合准备一张完整大脸。基础情绪决定默认口形和眉毛，眨眼只覆盖眼睛，短期惊讶/疼痛结束后回到之前情绪。眨眼不能重复重建角色或重置头发。

Cocos 接入时创建角色专用材质实例并缓存，只在状态改变时通过 `Material.setProperty` 更新图集参数，避免共用材质导致所有顾客一起变脸。专用 Effect 用 properties 声明对应参数；不在每次切表情时新建 Material 或切换 shader 宏。[材质脚本 API](https://docs.cocos.com/creator/3.8/manual/en/material-system/material-script.html)、[Effect 语法](https://docs.cocos.com/creator/3.8/manual/en/shader/effect-syntax.html)

## 微信预算与风险

以 512×512 RGBA8 为例，未压缩基础级约 1 MiB，完整 mip 约 1.33 MiB；本次 1024×512 对比图集基础级约 2 MiB。这是 GPU 像素存储估算，不是 PNG 下载大小。本页为便于技术比较使用未压缩 canvas 纹理且不生成 mip；正式版应离线制作纹理，按设备与画面尺寸验收压缩、边缘和 mip 串色。

平面方案可保留头部原绘制次数，增加少量纹理采样；具体 shader、采样次数和 draw call 必须在最终材质上测量。立体眼睛合并网格、共用材质，避免每个瞳孔独立创建复杂材质。不要为普通切表情每帧用 RenderTexture/Canvas 重画整张脸；不要依赖 UI 动态图集自动处理三维面部 UV。

只有脸部图案变化，不改变头皮位置，现有发根和碰撞缓存可以继续使用。若未来 Morph 涉及头顶/额头轮廓，则发根绑定与头模碰撞也要跟随形变，不能沿用静态缓存。

## 下一阶段验收

先定美术方向，再做一套正式脸部 UV 与 6–8 个眼嘴基础形态，接入 Cocos Effect；检查左右单眼、开心时眨眼、不同头型、侧后方无穿透、刘海遮挡。最后在 iOS/Android 微信同时运行剪发和表情，测 CPU/GPU 时间、draw call、纹理内存与十分钟切换稳定性。当前单人离线，无需新增网络同步。


## 已确认的表情需求与行为实现

用户确认：眼睛跟随玩家操作方向，时不时眨眼；眉毛参与开心、生气等表情；嘴巴表达笑、哭、惊讶。此轮据此实现共享 `character/FaceExpressionController.ts`，由预览驱动两种表现；尚未接入正式 Cocos 场景。

| 通道 | 当前行为 | 后续理发场景接入 |
| --- | --- | --- |
| 视线 | 鼠标移动或触摸拖动确定目标，约 0.1 秒量级平滑跟随，限幅；停止操作短暂停留后回正 | 从剪刀、梳子或手势的屏幕目标更新；不能与头部旋转操作混用 |
| 自动眨眼 | 每轮随机等待 2.5–5.5 秒，关闭约 80 ms、停留 40 ms、打开 140 ms | 与工具无关的局部表现；隐藏或暂停后不补播 |
| 眉毛 | 独立调整角度和高度，切情绪时逐渐过渡 | 情绪状态映射开心、内压生气、内侧抬起难过等姿态 |
| 嘴巴 | 独立切换平静、笑、惊讶张口、生气、哭泣口形 | 玩家反馈/顾客情绪驱动，不由眨眼计时器覆盖 |

当前跟随目标是“操作位置相对脸部的方向”，不是上一帧手指速度：慢慢移动也能看向目标，停止后不会突然反向。屏幕方向先逆变换到头部坐标；侧后方逐渐衰减追踪，避免背向玩家仍强行扭眼。正式版若存在真正三维工具，可把工具世界坐标转换到头部局部空间，再计算受限眼球转角；不用修改表情状态层。

两种眼睛都能满足此轮需求。平面方案只需独立眼白、瞳孔与眼睑区域；立体方案的价值主要在厚度、侧面和光照，并非眼神跟随的必需条件。现阶段推荐先以平面方案定美术，再根据侧面效果决定是否保留立体眼球。

新增专项检查：视线平滑/限幅/空闲回正、背面限制、自动与手动眨眼、眨眼期间保持哭或笑的口形、眉毛过渡、暂停恢复。全量 155 项中 154 通过，唯一失败仍为已有 physics 配置审计；类型检查通过。当前哭泣主要表现为眉毛和口形，未添加泪滴特效。
